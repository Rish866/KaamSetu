# Security foundation, product data layer and v1.4.0 screens (PR #2 + PR #3)

Replaces the permissive v1.3.0 schema with column-level grants, RLS and ~70 SECURITY DEFINER RPCs (migrations 202611200001/0002/0003), adds a deterministic matching engine, an email outbox, privacy export/deletion workflows, and rewrites every screen against those RPCs (mock data and `DemoContext` are gone). The database design is sound at the policy level: no direct writes to sensitive tables, `search_path = ''` everywhere, authorization inside each RPC, and 65 PGlite tests pass. The gaps are at the seams the PGlite harness cannot see: Supabase Auth (deletion, email confirmation, email change), concurrent workers, and moderation state changes that the employer can undo. Several UI, legal and docs statements are stronger than the implementation.

Watch for: (1) **confirmed** account deletion can never complete. `auth.users` is never removed, and removing it fails on `audit_events_actor_id_fkey`, so the email and phone stay reserved and the user can still sign in; (2) **confirmed** an employer can re-publish a job an admin paused or removed via `set_job_status`; (3) **confirmed** `outbox_claim` holds no lease, so two overlapping worker runs send every email twice, and users without a preferences row get an all-zero unsubscribe token; (4) **confirmed** `profiles.email_verified_at` and `profiles.email` are never synced from `auth.users`, so with the newly enabled email confirmation, team invitations cannot work for new employers and emails go to stale addresses after an email change; (5) **likely** `supabase config push` turns on email confirmation while docs say no email provider exists yet; (6) **confirmed** employers have no path to a resume, yet three user-facing texts promise it.

**Verdict**: NEEDS_CHANGES

## High-level view

The access model is the strongest part: every state change goes through an RPC that re-checks membership, status and the state machine, and column grants close the old escalation paths. The remaining RLS exposures are small: every authenticated user can read internal moderation text on approved companies, and verified companies can edit their identity fields after approval.

Moderation is only one-way. Admin `pause` and `remove` move a job to `paused` or `closed`, but the employer's own pause/close/reopen RPC allows `paused→published` and `closed→published` without checking who moved it there. The same pattern applies to the company-suspension path for jobs.

Account deletion is implemented as database anonymisation plus a "pending_service_role" note. Nothing performs the second half, and the first half leaves the Supabase Auth user fully functional. This contradicts the privacy copy, the retention table and the PGlite test that claims identifiers are freed.

The email pipeline works in the single-worker, single-run case. It breaks under overlap, ignores preference changes made after enqueue, silently skips every employer-side notification (`notify_company` bypasses the outbox), and its unsubscribe link is invalid for most users.

Auth configuration and the profile mirror drift apart. `config.toml` enables email confirmation and stricter passwords, but `profiles` copies `email`, `email_verified_at` and `phone` only at sign-up. Anything that depends on a verified or current email (team invitations, security alerts, contact disclosure) reads stale data.

Rollout is not safe as documented. The operations runbook applies the migration (step 3) four steps before the web build (step 7), while the audit doc says never to apply the migration first. v1.3.0 clients lose apply, post-job and discovery immediately, and existing v1.3.0 companies (status `pending`, no verification row) hide all their published jobs.

## Account deletion leaves the Auth user alive

`admin_process_deletion` anonymises `profiles`, removes profile sections, withdraws applications and records `auth_user_removal: pending_service_role` in the request result. Nothing in the repo implements that step (no `auth.admin` call anywhere, and `purge-storage.mjs` only touches storage). Consequences on real Supabase, all **confirmed** by reading the code except the GoTrue behaviour, which is **likely**:

- `auth.users` keeps the email, phone and password. GoTrue enforces unique email and phone, so re-registration is refused (or returns the obfuscated "already registered" user), and the old credentials still sign in. The profile then reads `status = 'deleted'`, the route guards bounce the user, but storage policies (`resume_object_insert`, `photo_object_insert`) and own-row table access do not look at status, so a "deleted" user can keep uploading.
- If the service-role step is added with `auth.admin.deleteUser`, it fails. `profiles.id` cascades from `auth.users`, but `private.audit_events.actor_id` references `profiles(id)` with no delete action (`202611160001:231`) and the immutability trigger forbids both `DELETE` and the `SET NULL` update. I reproduced this on the harness: after a processed deletion, `delete from auth.users` fails with `audit_events_actor_id_fkey`. `request_account_deletion` and `register_resume` both write audit rows, so every user who reaches this workflow is blocked. Employers additionally hit `application_events.actor_id`, `job_events.actor_id`, `interviews.created_by`, `job_invitations.sent_by`, `contact_disclosures.disclosed_to`, `abuse_reports.handled_by` and `privacy_requests.handled_by`, all plain FKs to `profiles`. The probe on an employer owner stopped earlier, on the last-owner trigger.

The PGlite test named "deletion anonymises and frees identifiers" (`tests/db/product.test.mjs:94,119-120`) passes because the harness `auth.users` table has no unique constraints and the test inserts a second `auth.users` row with the same email. It proves only that the `profiles` partial unique indexes are released.

A workable shape: make audit actor FKs `on delete set null` and let `deny_modify` permit the cascade only when the only changed column is `actor_id`; switch the other actor FKs to `set null` or keep a tombstone profile row; then run `auth.admin.deleteUser` from the privacy workflow (or a cron-driven worker) after `storage_paths_to_purge` is processed.

## Moderation can be reversed by the employer

`admin_review_job` maps `pause` to `paused` and `remove` to `closed` (`202611200001:732-733`). `set_job_status` (`:681-697`) lets any owner or recruiter move `paused→published` and `closed→published`, re-checking only company approval and `closes_at`. The UI exposes both as "Resume" and "Reopen" (`src/app/employer/jobs.tsx:45,47`). I reproduced both: after `admin_review_job(...,'remove')` the owner's `set_job_status(...,'published')` succeeded and the job was public again. Company suspension is handled (`admin_review_company` pauses jobs and `company_is_approved` gates publish), so the gap is job-level moderation only. `job_events` records the admin actor, so the data to distinguish exists.

## Outbox: no lease, dead unsubscribe, and enqueue-time suppression

`outbox_claim` selects due rows `for update skip locked` in a CTE and returns them without changing any column (`:519-531`). The row lock disappears when the RPC returns, so a second worker run (the cron fires every minute, the worker handles up to 50 rows sequentially) sees the same rows and sends them again. Reproduced: two consecutive claims returned the same three rows. `outbox_report` also does not check `status = 'pending'`, so a late report from the first run bumps attempts after a success.

`notification_preferences` rows are only created by `set_notification_preferences`. For everyone else `outbox_claim` returns the all-zero UUID (`:528`), the worker builds both the footer link and the `List-Unsubscribe` header from it, and `unsubscribe_by_token` finds no row and returns false, so the page says "This link is no longer valid". Reproduced for a user who never saved preferences. The harness test for unsubscribe first calls `set_notification_preferences(false)`, which creates the row and hides the problem.

`private.notify` decides `suppressed` versus `pending` when the row is created (`:488-491`), and only six kinds are optional. Everything else, including `invitation.received` (employer-initiated), is sent regardless of the toggle, while the footer text says "Stop optional update emails". `notify_company` (`202611200001:175`) never reaches the outbox, so three of the six "optional" kinds can never occur and employers get no email for new applicants or for company/job review results.

Subjects are the notification titles ("You were shortlisted", "You have an offer"), while the email body says "we never put application details in email". The subject itself discloses the outcome. Low severity, but the body claim is inaccurate.

## Profile mirror drifts from auth.users

`private.handle_new_user` copies `email`, `email_confirmed_at`, `phone` once at insert (`202611200001:228-231`). `config.toml` now sets `enable_confirmations = true`, so a new user has `email_confirmed_at = null` at insert and `profiles.email_verified_at` stays null permanently. `my_company_invitations` and `accept_company_invitation` require it non-null (`202611200002:608,617`), so invited employers can never join a team. The harness inserts `email_confirmed_at = now()` in `signUp`, and the invitation test flips the column by hand, so neither path exercises the real flow.

Email change (`SettingsView.tsx` `changeEmail`, `double_confirm_changes = true`) updates `auth.users.email` only. The new trigger `auth_users_security_change` then queues a "sign-in details changed" notice, which resolves its recipient from the stale `profiles.email` (the old address, which is right for a security alert), but every later email, `get_applicant_contact`, `admin_find_user` and invitation matching keeps using the old address. If password rehashing or provider-side updates touch `encrypted_password`, users also get "password changed" alerts they did not cause (**possible**, depends on GoTrue).

The same two triggers run inside GoTrue's own transactions. A failing `private.notify` (for example a `notifications` or outbox constraint) would make sign-up or password reset return 500 for everyone, with no isolation. `profiles_welcome` additionally queues a welcome email for every sign-up before confirmation, so the platform can be used to send mail to arbitrary third-party addresses.

## Rollout, ordering and data-dependent failures

The files are order-safe against the four earlier migrations (signatures, parameter names and constraint names match). Three things can still fail or surprise on a real database:

- Constraints that validate existing rows: `resumes_one_active` and `resumes_candidate_sha_active` (`202611200001:32-35`), `candidate_photo_owner`, and `companies_description_len` (`202611200002:554`). v1.3.0 had no resume upload, so the resume ones are unlikely, but a company description over 3000 characters would abort migration 0002. Run `select` pre-flights first.
- No object is guarded for re-run (`create table`, `add constraint`, `create policy`, `create trigger`, `insert into matching_versions`). Each file runs in one transaction under `supabase db push`, so a failure rolls back cleanly, but anything applied by hand beforehand will break the push. Migration 0003 is the only idempotent file and is correctly gated on `pg_available_extensions`, but it never ran in the harness (PGlite has no pg_cron), so the `cron.unschedule`/`cron.schedule` path is untested.
- Behaviour change for existing data: v1.3.0 created companies as `pending` with no verification row, while the new flow starts at `draft`. Under the new `jobs_public_read`, no company is approved until an admin acts, so every existing published job disappears. The admin queue left-joins verification rows, so an admin can approve a legacy company with no identifier on file.

The runbook (`docs/OPERATIONS.md:10-16`) applies the migration at step 3, `config push` at step 4 and the web build at step 7. `docs/AUDIT.md:64` says the opposite order. The migration revokes insert on `candidate_profiles`, `applications`, `consent_records`, column access to `discovery_enabled`, and forces job inserts to `draft`, so v1.3.0 web and APK clients (apply, post job, discovery toggle, profile upsert) fail immediately. The docs accept this for test APKs; the live web bundle is the larger exposure and needs a same-minute switch.

## Grants, defaults and what behaves differently on real Supabase

`alter default privileges for role postgres in schema public revoke execute on functions from public, ...` (`:11`) does not remove the global PUBLIC default. I created a new public function after the migrations on the harness and `anon` could execute it. Everything in 0001/0002 is covered by the explicit loops at the end of each file, but the comment promises more than the statement delivers, and the CI test only checks the functions that exist today. Default privileges are also set only `for role postgres`; tables or functions created by `supabase_admin` keep Supabase's anon/authenticated grants.

Other differences between PGlite and Supabase that matter here:

- Harness `auth.users` has no unique email/phone indexes, no `auth.identities`, no `updated_at`, and the harness signs users up with confirmation already set. Real GoTrue returns an obfuscated user with empty `identities` for an existing address when confirmation is on; `login.tsx` handles that path but nothing tests it.
- `service_role` is created with `bypassrls` but without any grants, so no test calls `outbox_claim`, `outbox_report`, `unsubscribe_by_token`, `run_retention_jobs` or `expire_stale_invitations` as `service_role`. On Supabase it holds execute through default ACLs and the migration revokes only from `public, anon, authenticated`, so the calls should work (**possible** risk only if project default ACLs differ). `outbox_claim` and the worker also run as `service_role` against `public` functions only, so missing USAGE on `private` is not an issue.
- Storage: `register_resume` reads `storage.objects.metadata->>'size'`, which the harness populates by hand. Real Storage writes it only after the upload completes; if it were absent the size check silently skips (`actual is not null`). `company-evidence` has no DELETE policy, so owners cannot remove a wrong upload, and an owner can upload to the folder of a suspended or approved company without limit.
- `config.toml` `[auth.sessions]` (`timebox`, `inactivity_timeout`) is a Pro-plan feature; on other plans the push will not apply it.

## Exposure through table-level grants

`grant select on public.companies to authenticated` is table-wide (`202611200001:481`). `companies_public_read` makes approved rows visible to any authenticated user, so a candidate account can read `verification_reason` (admin free text from approve/suspend/restore), `legal_name`, `registered_address` and `operating_locations`. Reproduced: the probe candidate read `verification_reason = "Documents checked"`. Anon is correctly limited to six columns. Owners may also update `display_name`, `website`, `description`, `city`, `industry`, `company_size`, `registered_address` and `operating_locations` after approval with no flag for re-review, so a verified brand name can be swapped for another.

`jobs` is granted to anon with all columns, including `created_by` (the recruiter's user id).

## Resumes: gating, scan status, employer access

`resume_object_read` (`:517`) allows the owner to read any object in their folder, whatever `resumes.scan_status` says. The Download button is disabled unless `scan_status = 'clean'` (`profile.tsx:119`), but a user can still call `createSignedUrl` themselves, so the sentence "cannot be downloaded until marked clean" in `docs/SECURITY.md:9` is a UI behaviour only. The exposure is limited to the file's own uploader. No code path sets `clean`, `infected` or creates `resume_extractions`, so Download stays disabled for everyone and the parsing review card never shows. Clients also control `p_sha256`, `p_mime` and the declared Content-Type; the server verifies size only.

The employer view has no resume access at all (`list_job_applicants` returns no file reference, storage allows only the owner). `profile.tsx:117` ("Employers only see it after you apply"), `legal.ts:13` ("Employers see your name, profile and resume only after you apply") and the store data-safety table describe a feature that does not exist. `legal.ts:12` also lists "messages with employers" as collected data, but there is no messaging.

## Unbounded matching and discovery cost

`search_candidates`, `my_job_matches` and `job_feed` call `private.match_score` per row, and each call runs several plpgsql sub-queries; `search_candidates` calls it twice per candidate before filtering and limiting (`:968-990`). Cost grows with total discoverable candidates or open jobs per request, and any approved company can invoke it repeatedly. The same function lets an employer page through every discoverable candidate with no volume limit beyond the 50-row page (audit rows are written but nothing reads them).

## Contact disclosure on unverified phone numbers

`get_applicant_contact` returns `profiles.phone`. With `[auth.sms] enable_confirmations = false` and `sms_sent = 0`, phone sign-ups are auto-confirmed without proof of ownership. The unique index `profiles_phone_unique` also lets an attacker claim a victim's number first, which makes the victim's sign-up fail with a database error. The employer sees a number the candidate never proved.

The notice version was `2026-11-19` in v1.3.0 and is `2026-11-18` now (`legal.ts:3`). Login and reset placeholders still say "Minimum 8 characters" (`login.tsx:170`, `reset-password.tsx:40`). `docs/IMPLEMENTATION_PLAN.md:86` says resumes are "scanned, parsed". The release note's "password and email change" is accurate, but the email-change flow leaves `profiles.email` stale as described above.

## Tests that assert less than they claim
